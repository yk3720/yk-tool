コンテキストエンジニアリング

Context Engineering for AI Agents

LLM AIエージェント Anthropic 2025年9月29日

この図解で使う基本用語

AIエージェント：LLMがツールをループ内で自律的に使い続けるシステム。単発の質問応答ではなく、複数ステップのタスクを自律実行する。

コンテキストウィンドウ：LLMが1回の推論で参照できるトークン列の最大長（例：200,000トークン）。この範囲内に収まる情報しかモデルは「見えない」。

トークン：LLMが扱うテキストの最小単位。日本語では1〜2文字程度、英語では1単語が目安。

プロンプトの書き方よりも、モデルに渡す情報全体のキュレーションが品質を決める。

コンテキストエンジニアリング

「何をモデルに渡すか・全体」を最適化。複数ターン・長期タスクが当たり前になった。

コンテキストとは、LLMがサンプリング時に参照するトークンの集合全体のこと。システムプロンプト・ツール定義・メッセージ履歴・外部データをすべて含む。

解決したかった根本問題：コンテキスト汚染（Context Rot）

LLMはTransformerアーキテクチャ上、全トークン間のペアワイズ注意計算（メモリ・計算コストが O(n²)）が必要。これはコストの問題だが、それとは独立した別の問題として、注意スコアのSoftmax正規化によってトークン数が増えると各トークンへの相対的な重みが希薄化する。さらにLLMの学習データには短いシーケンスのほうが多く、長距離依存の学習が十分でないという訓練分布の問題も重なる。これらが合わさって情報想起精度の低下を引き起こす。「ヘイスタック（Needle-in-a-Haystack）」型ベンチマークで実証されており、全モデルに共通して現れる特性。

このコードがやること：Softmax正規化によって注意の「相対的な希薄化」が起きる仕組みを示す（概念的な擬似コード）

# 各トークンへの注意重みはSoftmaxで正規化される（合計=1.0に）

scores = [dot(Q[i], K[j]) / sqrt(d_k) for j in range(n)]

weights = softmax(scores) # sum(weights) == 1.0

# → nが増えると1トークンあたりに配分される重みが相対的に減少

# ※ O(n²)はメモリ・計算コストの問題（別の話）

たとえ話①：100人の全体会議と発言の重み

会議の議事録に「重要度の合計を1.0に正規化して配分する」ルールがあるとする。2人の会議なら各発言に0.5ずつ配分できるが、100人になると各発言への配分は0.01。重要な発言でも埋もれる。LLMのSoftmax正規化された注意重みも、これと同じ構造でトークンが増えるほど1トークンあたりの重みが薄まる。

3まず理解する3つ

この3つを押さえれば、コンテキストエンジニアリングの本質を掴める。

01

コンテキスト汚染（Context Rot）

コンテキストウィンドウ内のトークン数が増えるほどモデルの情報想起精度が低下する現象。ソフトな性能曲線として現れ、ハードな「崖」ではなく全モデルに共通するグラデーションとして確認されている。コンテキストを「有限の貴重なリソース」として扱う根本的な理由。

02

注意予算（Attention Budget）

LLMが持つ「注意資源の総量」は有限。新しいトークンを追加するたびに予算が消耗される。人間のワーキングメモリと対応する概念。コンテキストエンジニアリングの本質は、この有限な予算を高品質なトークンだけに集中させる設計。

用語：Attention（注意機構）

Transformerにおける、各トークンが他のトークンへの関連度スコアを計算する仕組み。クエリ（Q）・キー（K）・バリュー（V）行列の内積演算で実現される。

03

ジャストインタイム取得（Just-in-time Retrieval）

全データを事前にコンテキストへ埋め込むのではなく、軽量な識別子（ファイルパス・URL・クエリ文字列）を保持し、必要なタイミングでツールを使って動的に取得する戦略。実行時のコスト増と引き換えに、コンテキスト汚染を大幅に抑制できる。

4主要概念・アーキテクチャ

A. コンテキストの構成要素と設計原則

基本指針：求める結果の確率を最大化する、最小限の高品質トークンの集合を見つける

システムプロンプト

Goldilocks Zone（ちょうどよい粒度）を狙う：

※童話『3匹のくまと少女』で「熱すぎず冷たすぎない、ちょうどよい」を意味する用語

過剰：if-elseロジックをハードコード → 脆くなる
不足：高レベルすぎて曖昧 → モデルが迷う
最小限かつ十分。XMLタグ等でセクション分け
ツール設計

エージェントと情報空間をつなぐ「契約」：

機能の重複なし・自己完結・エラー耐性あり
「どちらのツールを使うか迷う」設計はNG
入力パラメータは明確・非曖昧な命名
Few-shotサンプル（例示）

エッジケースを羅列するのではなく、多様で典型的なサンプルをキュレーションする。LLMにとって例は「千の言葉に値する絵」。

メッセージ履歴

そのまま積み上げず、不要なツール呼び出し結果は随時クリアする。コンテキストを「情報が密で引き締まった状態」に保つことが重要。

たとえ話②：引越しの荷造り

新居に全ての荷物を持っていく人はいない。「今すぐ必要なもの」だけを手荷物に、残りは必要になったら取り寄せる。コンテキストエンジニアリングはこの「荷造りの意思決定」に相当する。何をコンテキストという手荷物に入れるかが品質を左右する。

B. 長期タスク（Long-horizon Tasks）への対応技術

コンテキストウィンドウを超える長時間タスク（大規模コード移行・長期リサーチなど）のための3技術：

長期エージェントタスク開始
コンテキストウィンドウが上限に近づく
3つのアプローチから選択・組み合わせ
① コンパクション

会話を要約して新ウィンドウへ引き継ぐ

向き：往復の多い会話型タスク

② 構造的メモ取り

外部ファイルに書き出し、後で参照

向き：明確なマイルストーンがある開発

③ マルチエージェント

専門サブエージェントが分担し、サマリーのみ返す

向き：並列探索が有効なリサーチ

5初心者がはまりやすい落とし穴

① プロンプトにルールを詰め込みすぎる

エッジケースを想定するたびにシステムプロンプトへ追記し続ける。結果としてプロンプトが肥大化し、コンテキスト汚染を自ら引き起こす。

例：注文処理エージェントに「日本語の場合は〜、英語の場合は〜、返金は〜、クレームは〜、キャンセルは〜」と数十ルールを追記していくうちに、本来の注文処理ロジックへの注意が薄れ、ルール矛盾が多発した。

回避策：まず最小限のプロンプトでテスト。失敗パターンに応じて追記（最初から完璧を目指さない）。

② ツールセットを膨らませる

機能の幅を広げようと多数のツールを追加した結果、「どのツールを呼ぶべきか」がモデルにとって曖昧になる。人間が迷う設計でエージェントが迷わないはずがない。

例：ECサイトエージェントで「キャンセル」「返品」「返金」「注文変更」を別々のツールとして定義したところ、モデルがキャンセルと返品を頻繁に混同し、誤った操作を実行した。1つの「注文状態変更」ツールに統合することで解決。

回避策：ツールの責務を明確に分離し、機能の重複を徹底排除。最小限のツールセットで動作検証してから拡張する。

③「コンテキストウィンドウが大きければOK」という思い込み

100万トークンのコンテキストウィンドウが利用可能でも、コンテキスト汚染の問題は消えない。大容量でも長くなるほど精度は低下する。

回避策：ウィンドウサイズに関わらず、渡す情報の品質管理を怠らない。

④ コンパクションを積極的にしすぎる

「削れるだけ削る」とサマリーが粗くなり、後から見ると重要な判断の根拠が消えていることがある。重要性は文脈が進まないと分からない情報が存在する。

回避策：まずリコール最大化を優先。それから不要な内容を精度改善のために削るアプローチで調整する。

6専門用語集

用語 定義
コンテキストエンジニアリング
Context Engineering		 LLM推論時に最適なトークン集合をキュレーション・維持するための戦略の総体。プロンプト・ツール・履歴・外部データを含む全体を対象とする。
コンテキスト汚染
Context Rot		 コンテキスト内のトークン数増加に伴い、モデルの情報想起精度が低下する現象。Needle-in-a-Haystack（ヘイスタック）型ベンチマークで実証済み。
注意予算
Attention Budget		 「Softmax正規化により、コンテキストが長くなるほど1トークンあたりの注意重みが希薄化する」という現象を説明するためにAnthropicが使うメタファー。論文に定義された正式な技術用語ではなく、設計上の意思決定に使う比喩的枠組み。
コンパクション
Compaction		 コンテキストウィンドウの上限に達した際、会話履歴を要約して新コンテキストとして再起動する技術。Claude Codeが実装の代表例。
JIT取得
Just-in-time Retrieval		 全データを事前埋め込みせず、実行時に軽量な識別子をもとにツールで動的に取得する戦略。コンテキスト汚染を抑制しつつ大規模データを扱える。
段階的探索
Progressive Disclosure		 エージェントが探索を通じて徐々にコンテキストを発見するアプローチ（JIT取得と同じ考え方）。ファイルサイズ・命名規則・タイムスタンプをシグナルとして次の探索を判断する。
サブエージェント
Sub-agent		 マルチエージェントアーキテクチャにおいて、特定サブタスクを担当する専門エージェント。独自のクリーンなコンテキストで深掘りし、1-2Kトークンのサマリーのみを親エージェントに返す。
Few-shotプロンプティング
Few-shot Prompting		 期待する入出力のサンプルをコンテキストに含めることでモデルの出力を誘導する手法。多様で典型的な例のキュレーションが品質を左右する。
MCP
Model Context Protocol（モデルコンテキストプロトコル）		 モデルが外部ツール・データソースと標準的に接続するためのプロトコル。コンテキスト外部の情報を動的に取り込む仕組みの一つ。
Needle-in-a-Haystack
ヘイスタック型ベンチマーク		 長いコンテキストの中に特定の情報（針）を埋め込み、モデルが正確に参照できるかを評価するベンチマーク手法。コンテキスト汚染の実証に広く使われる。

7次に学ぶと良いもの

RAG（Retrieval-Augmented Generation）

ベクトルDB等による埋め込みベースの事前取得システム。JIT取得と組み合わせてハイブリッド戦略を構築する際の核心技術。

MCP（Model Context Protocol）

ツール接続の標準化プロトコル。エージェントの情報空間をプラグイン的に拡張する仕組みを理解する。

マルチエージェントシステム設計

オーケストレーター・サブエージェント間の通信設計、タスク分解戦略、エラー回復の仕組みを学ぶ。

Claude Code の実装パターン

Anthropicが実際のコーディングエージェントでコンテキストエンジニアリングをどう実装しているかを具体的に把握する。

Needle-in-a-Haystack ベンチマーク

コンテキスト汚染を定量評価する手法。どのモデルがどの長さで性能低下するかを実測する評価フレームワーク。

LLMの外部メモリ管理

Sonnet 4.5のmemory toolなど、コンテキスト外の永続ストレージへエージェントが情報を書き出す仕組みの設計パターン。
