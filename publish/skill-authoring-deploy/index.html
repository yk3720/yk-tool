Techmap AI / LLM

Anthropic Skills 作成ベストプラクティス

Claude に「再利用可能な能力」を追加するスキルの設計原則

ひとことで言えば

まずここだけ押さえる

Skills とは、Claude に「特定ドメインの知識・手順」を再利用可能な形で追加するプラグイン機構である。

SKILL.md という単一ファイル（YAML フロントマター＋本文）で定義し、Claude がタスクに応じて自動で読み込む。
設計の核心は 「簡潔さ」 と 「プログレッシブ開示（Progressive Disclosure）」 — コンテキストウィンドウを節約しながら必要な情報だけを届ける。

「コンテキストウィンドウ（Context Window）」とは？
LLM（Large Language Model：大規模言語モデル）が一度の推論で参照できるテキストの総量（トークン数で計量）。
システムプロンプト・会話履歴・スキルの内容・ユーザーの質問がすべてここに収まる有限リソース。
上限を超えると実装依存で 古いメッセージがトランケート（切り捨て）されるか、エラーが返るかのどちらかになる。
スキルの本文が長いほど会話履歴に使えるトークンが減る、というトレードオフが生じる。
どこで動くか？
claude.ai のプロジェクト機能

「プロジェクト」を作成し、スキルフォルダをアップロードする。プロジェクトを開いた時点（セッション開始時）に全スキルのメタデータが読み込まれ、チャット中に必要なスキル本文が都度読み込まれる。

Claude API（コード実装）

API 呼び出し時にスキルファイルを system prompt に含める形で渡す。ただし API ではネットワーク外部へのアクセスがないため、スクリプトの pip install 等は使えない。

「起動時」とは: claude.ai ではプロジェクトセッションの開始を指す。API では各リクエスト時にスキル内容を渡すため「毎回読み込み」となる。

対象読者
  • Anthropic の Claude API / claude.ai を使っているエンジニア
  • 繰り返し使う知識・手順を Claude に覚えさせたい人
  • エージェントや自動化ワークフローを構築したい人
この図解でわかること
  • SKILL.md の構造・書き方のルール
  • プログレッシブ開示パターンの設計方法
  • 自由度・フィードバックループの実装
  • 評価ファーストの開発プロセス

なぜ生まれたのか？

LLM の「毎回ゼロから教える問題」を解決するために

解決したかった課題

LLM は会話をまたいでコンテキストを保持しない。
「このプロジェクトの命名規則」「このDBのスキーマ」「このコードレビューの観点」— 毎回同じ背景知識をシステムプロンプトに書いていた。

Fine-tuning 高い（モデル自体に学習させる） なし 固定した大量の手順・スタイルの自動適用

スキルはメタデータ（name・description）だけが起動時にロードされ、本文は必要になった時点で初めて読み込まれる。 100個のスキルがあっても、関係ないスキルの本文はコンテキストを消費しない。

まず理解する3つ

これだけ押さえればスキル作成の骨格がわかる

1
簡潔さ最優先 — Claude はすでに賢い 必須

スキルのトークンは他の全情報（システムプロンプト・会話履歴など）と競合する。Claude がすでに知っていることは書かない。各記述に「このトークンは本当に必要か？」と自問する。

2
SKILL.md は目次 — 詳細は別ファイルへ 必須

SKILL.md 本文は 500 行以内。詳細情報は reference.md などに分離し、必要な時だけ読み込む「プログレッシブ開示」を実装する。参照の深さは1段階まで。

3
評価ファーストで開発する 推奨

スキルを書く前に、まず「スキルなしで Claude がどう失敗するか」を記録し、3つ以上の評価シナリオを作る。実際の失敗に基づいて最小限のスキルを書くことで、無駄な記述を防ぐ。

スキルの構造

SKILL.md の必須要件と命名規則

「YAML フロントマター（YAML Frontmatter）」とは？
ファイル冒頭の --- で囲まれたメタデータ領域。 YAML（YAML Ain't Markup Language：データシリアライズ言語）形式で記述する。
ソースコードのヘッダーコメント（// @author）に相当するが、機械が自動的に読み取る点が異なる。
このコードがやること

SKILL.md の最小構成。name（スキル識別子）と description（何をするか・いつ使うか）が必須フィールド。 起動時にこの2フィールドだけがすべてのスキルから読み込まれる。 

---
name: processing-pdfs
description: Extracts text and tables from PDF files, fills forms,
  and merges documents. Use when working with PDF files or when
  the user mentions PDFs, forms, or document extraction.
---

# PDF Processing

## Quick start
（本文。500行以内に収める）
フィールド 制約 ポイント
name 最大64文字・小文字/数字/ハイフンのみ・予約語（anthropic, claude）禁止 動名詞形（processing-pdfs）推奨
description 最大1024文字・空不可・XML タグ禁止 三人称で「何をするか＋いつ使うか」を両方記述

description の書き方：三人称ルール

良い例（三人称）
Processes Excel files and generates reports
悪い例（一人称・二人称）
I can help you process Excel files
You can use this to process files
なぜ三人称でなければならないのか？— 注入メカニズム

claude.ai は起動時に全スキルの description を連結して以下のような形のシステムプロンプトを自動生成する：

You have access to the following skills:
- processing-pdfs: Extracts text and tables from PDF files...
- analyzing-spreadsheets: Analyzes Excel data and generates reports...

ここに「I can help you process Excel files」と一人称が混入すると、システムプロンプト全体の一貫性が崩れ、Claude がどの主語で応答すべきかを誤判断する可能性がある。

プログレッシブ開示パターン

必要な情報を、必要なタイミングだけ読み込む設計

「プログレッシブ開示（Progressive Disclosure）」とは？
情報を一度に全部渡すのではなく、必要になったタイミングで段階的に開示する設計パターン。
百科事典の目次に相当する：全文を読まなくても、必要な項目のページだけ開ける。
たとえ話① ― 教科書と目次
SKILL.md は「教科書の目次」。Claude は目次だけ見て、必要な章だけ開く。全章を最初から読む必要はない。
目次にないページを Claude は自力で発見できない → SKILL.md に必ず参照先を書くこと。

推奨ディレクトリ構成

pdf-skill/
├── SKILL.md          # メイン（起動時に読み込み） ← 500行以内
├── FORMS.md          # フォーム記入ガイド（必要時のみ）
├── reference.md      # APIリファレンス（必要時のみ）
└── scripts/
    ├── analyze_form.py  # 実行するスクリプト
    └── fill_form.py

参照の深さは 1 段階まで

悪い例（2段階ネスト）
SKILL.md → advanced.md
              → details.md
                      → 実際の情報

Claude が途中で止まり情報を取りきれない可能性がある

良い例（1段階のみ）
SKILL.md → advanced.md（情報がここに）
SKILL.md → reference.md（情報がここに）

すべての参照先が SKILL.md から直接リンクされている

自由度の設定

タスクの性質に応じて指示の具体度を調整する

たとえ話② ― 崖のある橋 vs 広野
崖のある細い橋：安全な道は1本だけ → 低自由度（ガードレール付きの厳密な指示）
障害物のない広野：どこを歩いてもゴールに着く → 高自由度（方向だけ示す）
高自由度（テキストによる方針） 例：コードレビュー

複数のアプローチが有効・文脈依存の判断。
手順を列挙するだけで Claude が最適な方法を選ぶ。

中自由度（パラメータ付きテンプレート） 例：レポート生成

推奨パターンがある・設定で挙動が変わる場合。テンプレートを示しつつ変更可能な箇所を明示。

# スキル内での記述例（中自由度）
## レポート生成

このテンプレートを使い、必要に応じてカスタマイズすること：

def generate_report(data, format="markdown", include_charts=True):
    # データを処理する
    # 指定フォーマットで出力
    # include_charts=True なら可視化も含める
低自由度（完全なコマンド） 例：DB マイグレーション

操作が脆弱・順序固定・一貫性が必須の場合。
「このコマンドをそのまま実行し、フラグを追加しないこと」と明記。

python scripts/migrate.py --verify --backup
# このコマンドを変更・追記しないこと

フィードバックループの実装

品質が重要なタスクでは「検証 → 修正 → 繰り返し」ループを明示的に組み込む。

たとえ話③ ― コンパイル→テスト→修正サイクル
プログラムのビルドパイプラインと同じ構造：
コード変更 → make test → 失敗 → 修正 → 再テスト → 全テスト通過後にのみマージ。
スキルでも「validate.py を実行 → 失敗したら修正 → 再実行 → 通過後のみ次へ」と書くことで同等の安全性を担保できる。
チェックリスト付きワークフローの書き方

Claude とユーザーが進捗を共有できるよう、コピー可能なチェックリストとして提示する。

## タスク進捗
- [ ] Step 1: フォームを解析する（analyze_form.py を実行）
- [ ] Step 2: フィールドマッピングを作成する（fields.json を編集）
- [ ] Step 3: マッピングを検証する（validate_fields.py を実行）
- [ ] Step 4: フォームに記入する（fill_form.py を実行）
- [ ] Step 5: 出力を確認する（verify_output.py を実行）

# Step 3 が失敗した場合は Step 2 に戻る

開発イテレーション

評価ファースト × Claude A/B 方式でスキルを磨く

Claude A / Claude B 方式

たとえ話④ ― 仕様作成者と実装者の分業
ソフトウェア開発での「仕様設計者（Claude A）」と「実装者（Claude B）」の役割分担と同じ。
設計者がドキュメントを書き、実装者が実際に動かしてみてフィードバックを返すサイクル。
具体的な操作手順（claude.ai の場合）
  1. Claude A（設計セッション）：新しいチャットを開き、タスクを会話で実行。繰り返し使う知識・手順を特定して「SKILL.md を作成してください」と依頼する。
  2. 生成された SKILL.md をファイルに保存し、プロジェクトのスキルフォルダに追加する。
  3. Claude B（テストセッション）：スキルを追加したプロジェクトで別の新チャットを開き、実際のタスクを投げる。
  4. Claude B の挙動を観察して問題をメモし、Claude A セッションに持ち帰って SKILL.md を改善する。

「2 つのセッション」の正体は 物理的に別タブで開いた別チャット。Claude A = 設計・改善担当のチャット、Claude B = スキルを実際に使うプロジェクトチャット。

Claude A（設計者）
  • ・タスクを実際にやってみる
  • ・繰り返し使う知識・手順を特定する
  • ・SKILL.md を作成・改善する
  • ・過剰説明を削る
スキルを渡す 問題を報告
Claude B（実行者）
  • ・スキルをロードした状態で実際のタスクを実行
  • ・どこで詰まるかを露わにする
  • ・予期しないファイル参照パスを取る
  • ・ルール適用漏れを起こす

評価ファースト開発プロセス

1
スキルなしで Claude にタスクを実行させる — 失敗点・不足コンテキストを記録
2
3つ以上の評価シナリオを作る — 実際に起きた失敗をテストケースに
3
ベースラインを計測する
4
最小限のスキルを書いてギャップだけを埋める — 予想で書かない
5
評価を実行し、改善を繰り返す
評価シナリオの書き方（JSON 形式の例）

使用スキル・クエリ・期待動作の3要素で構成する。これをベースに手動またはスクリプトで Claude の応答を採点する。

{
  "skills": ["pdf-processing"],
  "query": "このPDFからテキストを抽出して output.txt に保存して",
  "files": ["test-files/document.pdf"],
  "expected_behavior": [
    "pdfplumber など PDF ライブラリを使ってファイルを読み込む",
    "全ページのテキストを欠落なく抽出する",
    "output.txt に読みやすい形式で保存する"
  ]
}

初心者がはまりやすい落とし穴

よくある失敗パターンと回避策

Windows スタイルのパスを書く
scripts\helper.py と書くと Unix 環境（claude.ai 等）でエラーになる。
回避策：常にスラッシュ scripts/helper.py を使う。OS に関わらず動作する。
参照を 2 段階以上ネストする
SKILL.md → A.md → B.md のように深くすると、Claude がファイル読み取りツール（bash の head -n 100 コマンド相当）でファイルを途中まで読んで止まり、B.md の内容が欠落する。
（Claude はファイル内容をシェルコマンドで読み込む。リンクされた先のファイルが大きい場合、全文ではなく冒頭部分だけ読んで判断することがある。）
回避策：全参照先を SKILL.md から直接リンクし、参照チェーンは1段階に留める。
時間依存の条件分岐を書く
「2025年8月以前は旧 API を使用」などと書くとスキルが古くなった時に誤動作する。
回避策：現在の方法をメインに書き、旧情報は Markdown の <details><summary>...</summary>...</details> タグで折り畳む。
（Markdown は HTML タグをそのまま通すため、GitHub や claude.ai で <details> は折りたたみブロックとして機能する。Claude はこのブロックを「非推奨/旧情報」のシグナルとして認識し、通常フローでは参照しない。）
MCP ツール名をサーバー名なしで書く
MCP（Model Context Protocol：モデル コンテキスト プロトコル）ツールを bigquery_schema とだけ書くと「tool not found」エラーになる。
回避策：BigQuery:bigquery_schema のように「サーバー名:ツール名」形式で書く。
スクリプトでエラーを Claude に丸投げする
return open(path).read() のようにエラー処理なしで書くと、ファイルが存在しない場合に Claude が「どう対応すべきか」を推測し始める。
回避策：try/except でエラーを処理し、デフォルト値を返すか具体的なエラーメッセージを出す。

専門用語集

スキル設計を理解するうえで押さえておく語

コンテキストウィンドウ（Context Window）
LLM が1回の推論で参照できるテキストの総量。スキル・会話履歴・システムプロンプトがすべて競合する有限リソース。
プログレッシブ開示（Progressive Disclosure）
必要になった時点で段階的に情報を渡す設計パターン。SKILL.md を目次として機能させ、詳細は別ファイルに分離する基盤概念。
YAML フロントマター（YAML Frontmatter）
ファイル冒頭の --- で囲まれたメタデータ領域。name と description の2フィールドが必須。起動時に全スキルからこの部分だけが読み込まれる。
動名詞形（Gerund Form）
「動詞 + -ing」の形（processing / analyzing / managing）。スキル name の推奨命名規則。何をするスキルかが一目でわかる。関連：命名規則
フィードバックループ（Feedback Loop）
「実行 → 検証 → 修正 → 再実行」を繰り返す反復プロセス。スクリプトの validate.py を使って機械的に検証し、エラー時は自動で修正フェーズに戻る。
MCP（Model Context Protocol：モデル コンテキスト プロトコル）
Claude が外部ツールや API を呼び出すためのプロトコル。スキル内でツールを参照する際は「サーバー名:ツール名」形式（例：BigQuery:bigquery_schema）が必須。
評価シナリオ（Evaluation Scenario）
スキルの有効性を測るテストケース。使用スキル・クエリ・期待動作の3要素で構成。スキル作成前に最低3つ用意することを推奨。

次に学ぶと良いもの

このスキル知識の先にあるトピック

Anthropic Skills 概要（Skills Overview）
スキルのアーキテクチャ・ランタイム環境の詳細。ファイルシステムベースの設計思想を理解できる。
MCP（Model Context Protocol）
Claude が外部ツールを呼び出すプロトコル。スキルと MCP を組み合わせることで API 連携が可能になる。
プロンプトエンジニアリング（Prompt Engineering）
スキルの本文自体がプロンプト。Few-shot・Chain-of-Thought などの技法はスキル設計にそのまま応用できる。
Claude API エージェント設計
スキルを複数組み合わせて複雑なエージェントを構築する。Tool Use・Computer Use との連携パターン。
プロンプト設計パターン（Few-shot / Chain-of-Thought）
Few-shot（数ショット学習）：入出力ペアの例を数件見せることで Claude の出力スタイルを制御する手法。スキルの「入出力例パターン」の理論的根拠になる。
Chain-of-Thought（思考の連鎖）：「ステップごとに考えて」と指示して推論精度を上げる手法。スキルのワークフロー設計に応用できる。
どちらもスキル本文を書く際に直接使えるプロンプト設計の基礎知識。
