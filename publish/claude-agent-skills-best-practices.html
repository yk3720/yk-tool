なぜ生まれたのか

解決したかった課題

LLM（Large Language Model：大規模言語モデル）——大量のテキストデータで事前学習された生成AIモデル。Claude もその一種。  |  システムプロンプト（System Prompt）——会話開始前に Claude の動作指針・役割・制約を与える隠し指示文。ユーザーの会話とは別にバックグラウンドでロードされる。

LLM に特定の操作を覚えさせるには、毎回システムプロンプトに長い説明を書くしかなかった。これは3つの問題を生む：

  • ① コンテキストの浪費——同じ説明が会話ごとにコンテキストウィンドウを圧迫する
  • ② 再利用不可——チームで共通の手順を使い回せない
  • ③ 属人化——「誰かのプロンプト職人技」として散在し、品質がばらつく

Agent Skills の誕生

Anthropic は SKILL.md というファイル形式でスキルをカプセル化し、Claude がタスクに応じて必要なスキルだけをオンデマンドで読む仕組みを設計した。 「必要な時だけ読む（プログレッシブディスクロージャー）」によりトークンを節約しつつ、再利用・共有ができる。

時系列イメージ：
毎回長い説明を書く時代 → システムプロンプトへの埋め込み → スキルとして外部化・オンデマンドロード

まず理解する3つ

1

SKILL.md の構造を理解する

スキルの核は SKILL.md 1ファイル。YAMLフロントマターに name（発見キー）と description（トリガー条件）を書き、本文に指示を書く。本体は500行以下が目安。

YAML フロントマター（YAML Front Matter）——マークダウンファイルの先頭に書く --- で囲まれたメタデータ領域。スキルでは name と description の2フィールドが必須。
SKILL.md 最小構成例
--- name: processing-pdfs description: PDF ファイルからテキストと表を抽出します。 PDFやドキュメント抽出を扱う場合に使用します。 --- # PDF 処理 ## クイックスタート pdfplumber でテキストを抽出します： ```python import pdfplumber with pdfplumber.open("file.pdf") as pdf: text = pdf.pages[0].extract_text() ``` ## 高度な機能 **フォーム入力**：詳細は [FORMS.md](FORMS.md) を参照してください
2

プログレッシブディスクロージャーの仕組み

Claude はスタートアップ時にすべてのスキルの name + description だけを読み込む。タスクに関連すると判断したスキルの SKILL.md を初めて読む。さらに詳細が必要な場合のみ参照ファイル（FORMS.md など）を読む。

プログレッシブディスクロージャー（Progressive Disclosure）——必要になるまで情報をロードしない設計原則。ソフトウェアUIの「詳細設定を折りたたむ」と同じ発想。

ロードの流れ

会話セッション開始時
全スキルの name + description だけシステムプロンプトにロード
ユーザーが PDF について質問
pdf-processing スキルの SKILL.md をロード
フォーム入力が必要と判断
FORMS.md を追加ロード
sales.md、finance.md などは
コンテキストトークンを消費しない
3

Claude A / Claude B による反復開発

スキルを改善するには「書く人」と「使う人」を分けるのが効果的。Claude A（スキル設計担当）が SKILL.md を作り、Claude B（実作業担当、スキルをロード済み）が実際に使う。Claude B の失敗観察 → Claude A へのフィードバック → 修正、このサイクルが最速の改善手段。

「別インスタンス」の操作方法——Cursor では別のチャットウィンドウ（タブ）、claude.ai では別の会話セッションを開く。Claude Code ならプロジェクトを別に立ち上げる。重要なのは Claude A のコンテキスト（会話履歴）を Claude B が引き継がないこと。スキルを実際に読み込ませた「フレッシュな Claude」で実タスクをテストする。

たとえ話：製品開発チームの分業

「製品仕様を書くPM（Claude A）」と「実際に使うユーザー（Claude B）」を分けてテストするのと同じ。仕様書を書いた人間が自分でテストすると都合よく解釈してしまうため、別インスタンスが必要。

主要概念・アーキテクチャ

コア原則3つ

原則1：簡潔さが重要

コンテキストウィンドウ（Context Window：Claude が一度に扱えるトークン数の上限）は公共財。スキルのトークンは、システムプロンプト・会話履歴・他スキルと競合する。Claude が既に知っていることは書かない。

良い例（約50トークン）

## PDF テキストの抽出 ```python import pdfplumber with pdfplumber.open("file.pdf") as pdf: text = pdf.pages[0].extract_text() ```

悪い例（約150トークン）

## PDF テキストの抽出 PDF (Portable Document Format) は テキスト、画像を含む形式です。 抽出にはライブラリが必要で、 pdfplumberが推奨されます。まず pip でインストールする必要があります...

原則2：適切な自由度を設定する

「崖のある狭い橋 vs 広大な野原」——操作の危険度・可逆性に応じて Claude への裁量（橋の幅）を調整する。崖＝不可逆な失敗リスク。橋の幅が広いほど Claude が多くのアプローチを選べる。崖がない広大な野原では、どのルートを選んでも失敗しない。下表の「自由度」が「橋の幅」に対応する。

自由度 記述スタイル 使う場面
高い テキスト指示（方針・ヒューリスティック） コードレビュー、文書要約など柔軟判断が有効な場面
中程度 疑似コード・テンプレート（パラメータあり） レポート生成など推奨パターンはあるが多少の変動が許容できる場面
低い 特定のスクリプト（変更禁止） DBマイグレーション、本番デプロイなど一貫性・順序が重要な場面

原則3：全モデルでテストする

スキルはモデルの補助として機能する。Haiku（Claude Haiku）では詳細なガイダンスが必要、Sonnet（Claude Sonnet）では効率性を重視、Opus（Claude Opus）では過剰説明を避ける——各モデルの能力に合わせた調整が必要。

スキルのファイル構造

スキルはディレクトリ単位で管理する。SKILL.md から 1レベル深い参照ファイルへのリンクが基本構造。深くネストすると Claude が中間ファイルをファイルシステムとして探索する際に、巨大ファイルの冒頭部分しか読まずに内容の全体像を誤認し、情報が不完全になる。SKILL.md 本体は500行以下が推奨——これを超えると Claude が関連する他のコンテキストと競合し推論品質が落ちることが実験的に確認されているため。

推奨ディレクトリ構造（PDF処理スキルの例）
pdf/ ├── SKILL.md # メイン指示（トリガー時にロード） ├── FORMS.md # フォーム入力ガイド（必要時のみロード） ├── reference.md # API リファレンス（必要時のみロード） ├── examples.md # 使用例（必要時のみロード） └── scripts/ ├── analyze_form.py # ユーティリティスクリプト（実行される） ├── fill_form.py # フォーム入力スクリプト └── validate.py # 検証スクリプト

たとえ話：図書館の参考資料棚

SKILL.md は「館内案内図」、参照ファイルは「各書架」、スクリプトは「実際に処理をやってくれる司書」。来館者（Claude）は案内図を見て必要な書架だけへ行く。全書架の中身を最初から暗記させる必要はない。

効果的な description の書き方

description はスキル発見の鍵。起動時に全スキルの description がシステムプロンプトに一括挿入され、Claude はユーザーのリクエストと description を比較してどのスキルを使うか推論で判断する（キーワードマッチではなく意味的な照合）。100以上のスキルの中から正しいスキルを選ぶ手がかりはこの description だけ。三人称で、何をするかといつ使うかの両方を含める。

三人称で書く理由——description はシステムプロンプトに「スキル一覧」として挿入される。「Excel ファイルの処理をお手伝いできます」のような一人称だと、Claude が自分自身の発言として読んでしまい「自分はすでにこのことを言った」と混乱する可能性がある。「Excel ファイルを処理してレポートを生成します」のような三人称なら「このスキルが提供する能力」として正しく解釈できる。

良い例

description: PDF ファイルからテキストと表を抽出し、フォームに入力し、ドキュメントをマージします。PDF ファイル、フォーム、またはドキュメント抽出について言及されている場合に使用します。

悪い例

description: ドキュメントを支援します

→ 何をするか不明。いつ使うかも不明。

視点の誤り（一人称）

description: Excel ファイルの処理をお手伝いできます

→ システムプロンプトへの挿入時に視点が混乱する。三人称で書くこと。

チェックリスト形式ワークフロー

複数ステップの操作には、Claude がコピーして使えるチェックリストを提供する。これにより 重要な検証ステップのスキップを防ぐ。

フィードバックループ——バリデータを実行 → エラーを修正 → 再実行、のサイクル。早期にエラーを検出し出力品質を大幅に向上させる。
チェックリストパターンの例
## PDF フォーム入力ワークフロー タスクの進行状況： - [ ] ステップ 1：フォームを分析する (analyze_form.py を実行) - [ ] ステップ 2：フィールドマッピングを作成する - [ ] ステップ 3：マッピングを検証する (validate_fields.py を実行) - [ ] ステップ 4：フォームに入力する (fill_form.py を実行) - [ ] ステップ 5：出力を確認する (verify_output.py を実行) ## ステップ 3：マッピングを検証する 実行：python scripts/validate_fields.py fields.json 続行する前に検証エラーを修正します。

たとえ話：航空機の離陸前チェックリスト。パイロットが「スキルがあるから確認しなくて良い」とはならない。チェックリストは忘却・油断を防ぐ安全装置。

評価駆動開発（Eval-Driven Development）

広範なドキュメントを書く前に、まず評価（テストケース）を作る。「スキルなしで Claude がどこで失敗するか」を先に特定し、その問題だけを解決する最小限のスキルを書く。

①ギャップ特定

スキルなしで失敗を記録

②評価作成

3つのシナリオを構築

③反復

評価→比較→改善

「3つのシナリオ」の具体的な書き方

各シナリオは { skills, query, files, expected_behavior[] } の形式で記述する。TDDのユニットテストに相当する。

{ "skills": ["pdf-processing"], "query": "この PDF からすべてのテキストを抽出して output.txt に保存", "files": ["test-files/document.pdf"], "expected_behavior": [ "pdfplumber など適切なライブラリでPDFを読み込む", "全ページからテキストを漏れなく抽出する", "抽出テキストを output.txt に保存する" ] }

3つの代表的なユースケース（正常系・エッジケース・失敗系）をカバーするシナリオを用意するのが目安。

初心者がはまりやすい落とし穴

落とし穴①：Claude が知っていることまで書いてしまう

「pdfplumber は PDF 処理ライブラリです。pip install pdfplumber でインストールします。PDF とは...」のように、Claude が既知の内容まで書くとトークン浪費になる。

回避策：各文に「Claude はこれを知らないか？」と問い直す。知っていれば削除。

落とし穴②：参照ファイルを深くネストする

SKILL.md → advanced.md → details.md のような3層構造にすると、Claude が途中のファイルを head -100 で部分読みして情報が不完全になる。

回避策：SKILL.md から1レベル深い参照のみ。すべての参照ファイルを SKILL.md から直接リンク。

落とし穴③：選択肢を多く提示しすぎる

「pypdf、または pdfplumber、または PyMuPDF、または pdf2image、または...」のように複数の選択肢を並べると Claude が迷い、一貫性のない実装になる。

回避策：デフォルトを1つ決めてエスケープハッチを添える

「テキスト抽出には pdfplumber を使います。スキャンされた PDF で OCR が必要な場合のみ pdf2image + pytesseract を使います。」

落とし穴④：時間に敏感な記述を使う

「2025年8月前はv1 APIを、以降はv2 APIを使います」のような日付ベースの条件分岐はスキルが陳腐化した時に誤動作する。

回避策：「現在の方法」と「古いパターン（折りたたみ表示）」セクションに分ける。

落とし穴⑤：Windows スタイルのパスを書く

scripts\helper.py のようなバックスラッシュは Unix 系環境でエラーになる。

回避策：Windows 環境でもフォワードスラッシュ（scripts/helper.py）を使う。

落とし穴⑥：スクリプトのエラーを Claude 任せにする

return open(path).read() のようにエラー処理を省略すると、失敗時に Claude が独自の対処をして予期しない動作になる。

回避策：FileNotFoundError・PermissionError などを明示的に処理し、デフォルト動作を定義する。

専門用語集

用語 定義
LLM
Large Language Model（大規模言語モデル）		 大量のテキストデータで事前学習された生成AIモデル。Claude・GPT・Gemini などが該当する。スキルはこの LLM の動作を補強する仕組み。
システムプロンプト
System Prompt		 会話開始前に Claude の動作方針・役割・制約を与えるバックグラウンド指示文。スキルの description はここに挿入され、Claude がスキル選択の判断に使う。
Agent Skills
エージェントスキル		 Claude に再利用可能な専門能力を付与するファイル群。SKILL.md を中心に参照ファイルやスクリプトで構成される。
SKILL.md スキルのエントリーポイントとなるマークダウンファイル。YAMLフロントマター（name + description）と本文指示で構成。500行以下が推奨。
Context Window
コンテキストウィンドウ		 Claude が一度の推論で参照できるトークン数の上限。システムプロンプト・会話履歴・スキル内容がすべてここに収まる必要がある。
Progressive Disclosure
プログレッシブディスクロージャー		 必要になるまで情報をロードしない設計原則。スキルでは「名前・説明 → SKILL.md → 参照ファイル」の順でオンデマンドロードされる。
YAML Front Matter
YAMLフロントマター		 マークダウンファイル先頭の --- で囲まれたメタデータ領域。スキルでは name（識別子）と description（発見トリガー）の2フィールドが必須。
MCP
Model Context Protocol（モデルコンテキストプロトコル）		 外部ツール・APIをClaudeから呼び出すための標準プロトコル。スキルから参照する際は ServerName:tool_name の完全修飾形式を使う。
Eval-Driven Development
評価駆動開発		 スキルを書く前にテストケース（評価）を作り、それをパスする最小限のスキルを書くアプローチ。TDD（テスト駆動開発）のスキル版。
Claude A / Claude B パターン スキル設計担当（Claude A）と実作業担当（Claude B）を別インスタンスにして反復改善するアプローチ。Claude B の失敗観察が改善の起点。
Magic Constants
魔法の定数（マジックナンバー）		 根拠なく埋め込まれた数値・設定値（例：TIMEOUT = 47）。スクリプト中では必ずコメントで理由を説明する。
Feedback Loop
フィードバックループ		 「バリデータ実行 → エラー修正 → 再実行」のサイクル。スキルのワークフローに組み込むことで出力品質を大幅に向上させる。
