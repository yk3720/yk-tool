シンタックスとセマンティクス

「形式」と「意味」を分けて考える技術

ひとことで言えば

シンタックスは「正しく書かれているか（形式）」、セマンティクスは「書いた内容が意図どおりの意味を持つか（内容）」を扱う。この2つを分けて考えることで、エラーの種類・検出タイミング・検証手法が明確になる。

シンタックス（Syntax）

記号・単語を並べる際の形式ルール。
「どう書くか」 — How to write

コンパイル前・実行前に検出可能

セマンティクス（Semantics）

その記述が表す意味・意図・論理。
「何を意味するか」 — What it means

実行して初めて顕在化するバグも多い
対象読者： プログラミング経験がある技術者。言語処理系・型システム・静的解析に踏み込む前の整理として。

なぜ生まれたのか

この分類は1950年代の言語学と計算機科学の接点から生まれた。

チョムスキーの生成文法（1950年代〜）

ノーム・チョムスキー（Noam Chomsky）は、自然言語の文法を「有限の規則から無限に文を生成できる形式体系」として定式化した。この際、「文法的に正しいこと（シンタックス）」と「意味が通ること（セマンティクス）」を意図的に分離して記述しようとした。 その成果として「チョムスキー階層」が生まれ、文法の表現力をオートマトン（計算機）と対応させた分類が確立した。

コンパイラ設計への波及

BNF（Backus-Naur Form：バッカス・ナウア記法）や CFG（Context-Free Grammar：文脈自由文法）により、プログラミング言語の構文を機械可読な形で記述できるようになった。 コンパイラは「字句解析 → 構文解析 → 意味解析 → コード生成」という段階的なパイプラインを持つことで、構文エラーと意味的エラーを別フェーズで検出できる設計になった。

解決した課題

「どの文字列がその言語に属するか（受理問題）」と「そのプログラムが何をするか（振る舞い・型の一貫性）」を明確に分けることで、ツール（コンパイラ・リンター・型検査器）の設計と、エラーメッセージの品質が劇的に向上した。

まず理解する3つ

1

シンタックスエラーは「書き方の誤り」

カッコの閉じ忘れ・== と書くべき場所に = を書く・インデントミス。パーサが実行前に検出できる。文法規則（BNF/CFG）に照らして機械的に判定可能。

2

セマンティクスエラーは「意味の誤り」

b + c と書くべき場所に b - c と書く・無限ループ・誤った条件式。文法は正しくても論理として意図通りでない。実行して初めて発覚するものも多い。

3

コンパイラは2段階で検査している

「構文解析（Syntax Analysis）」でシンタックスを、「意味解析（Semantic Analysis）」でセマンティクス（型・スコープ・未定義参照）を検査する。型エラーは多くの場合意味解析フェーズの産物。

主要概念・アーキテクチャ

シンタックスとセマンティクスは、コンパイラ内の「どのフェーズで検査されるか」で明確に分離されている。

たとえ話で理解する

たとえ話 1 ：レシピの書き方 vs 料理の出来栄え

シンタックスは「レシピの書き方ルール（材料は箇条書き・手順は番号付き・単位は g/ml で統一）」。このルールを守らないと、料理本の編集者に突き返される（コンパイルエラー）。
セマンティクスは「そのレシピで作ると本当においしいか」。書き方は正しくても「塩 10 kg」と書けばまずい料理ができる（論理バグ）。

たとえ話 2 ：「無色透明な緑色のアイデアが激しく眠る」

チョムスキーが示した有名な例文。「無色透明な緑色の〜」は文法（シンタックス）的には正しい構造を持つが、意味（セマンティクス）として矛盾している（無色透明なものが緑色にはなれない）。プログラムでも同様に、文法を通過しても意味が破綻するコードは書ける。

たとえ話 3 ：工場の2段階品質検査

第1検査（書類審査 ＝ シンタックス）：部品の形が規格書通りか。不正な形なら即却下。
第2検査（動作確認 ＝ セマンティクス）：形が規格通りでも、実際に組み立てると動くか。この段階で初めて「かみ合わない部品」（論理バグ）が発覚する。
コンパイラの構文解析と意味解析はちょうどこの2段階に対応している。

シンタックスエラーの例

このコードは「比較演算子の誤り」と「括弧の欠落」という書き方ルール違反を示す。

# シンタックスエラー：実行前に検出される
if x = 1:          # SyntaxError: 代入演算子 = を比較に使用（正しくは ==）
    print("one")

result = (a + b    # SyntaxError: 括弧が閉じられていない

セマンティクスエラーの例（動的：実行時に発覚）

このコードは文法的に正しいが、「割引後の価格」を計算する意図で書かれているのに引き算と足し算が逆になっているという論理バグを示す。

# セマンティクスエラー（動的）：文法は通過するが意味が誤り
def discounted_price(price, discount_rate):
    # 意図: 割引後の価格 = price × (1 - discount_rate)
    return price * (1 + discount_rate)  # 誤: 割増になっている

# Python は何のエラーも出さず実行する
print(discounted_price(1000, 0.1))  # → 1100（本来 900 のはず）

型エラーは「静的セマンティクス」エラー

このコードはシンタックス（文法）的には正しい。しかし型規則（意味）に違反するため、TypeScriptとJavaはコンパイル時に弾く。「型エラー ＝ 実行後に発覚」ではなく、「静的意味解析フェーズで検出」される。

// TypeScript: 型注釈はシンタックス拡張、型検査は静的セマンティクス
const x: number = "hello";
// TS2322: Type 'string' is not assignable to type 'number'
// → 文法は通過するが、意味解析（型検査）フェーズで拒否される

// Java: 静的型付きでコンパイル時に型整合を検証
int count = "hello";
// error: incompatible types: String cannot be converted to int
// → 実行前にコンパイルエラーとして検出（実行時エラーではない）

HTMLにおける対応関係

HTMLにも同様の区別がある。

Syntax（書き方のルール）

  • タグの開始・終了の対応
  • 属性値の引用符
  • 文字参照のエスケープ

Semantics（意味・役割）

  • <button> vs <div onclick>
  • 見出しレベルの論理的順序
  • アクセシビリティ・スクリーンリーダー上の意味
なぜ <button> と <div onclick> は「意味が違う」のか：
見た目は同じにできても、<button> はキーボードフォーカス・Enterキー送信・WAI-ARIA ロール「button」・スクリーンリーダーへの「ボタン」読み上げが自動付与される。<div onclick> はクリックイベントは走るが、これらの「意味的な役割」が欠落している。シンタックスは通過しても、アクセシビリティ上のセマンティクスが破綻している典型例。
AST（Abstract Syntax Tree：抽象構文木）
構文解析の出力。「括弧は省いた」「演算子の優先順位を木構造に変換した」状態の中間表現。意味解析はこの木に対して行われる。
BNF（Backus-Naur Form：バッカス・ナウア記法）
プログラミング言語の文法（シンタックス）を生成規則の形式で記述する表記法。例：<expr> ::= <term> | <expr> "+" <term>。繰り返しや省略を簡潔に表記した拡張版が EBNF（Extended Backus-Naur Form：拡張バッカス・ナウア記法）。
CFG（Context-Free Grammar：文脈自由文法）
BNF で表現される文法クラス。多くのプログラミング言語の構文はこのクラスに収まる。プッシュダウンオートマトン（スタックを持つ有限状態機械）で解析できる点が重要な数学的性質。チョムスキー階層の第2クラス。
受理問題（Acceptance Problem）
形式言語理論の文脈で「ある文字列がその文法（言語）に属するか否かを判定する問題」のこと。シンタックスの仕事は、入力コードをこの受理問題として扱い、文法に合致すれば受理（パス）・違反すれば拒否（構文エラー）と判定すること。

初心者がはまりやすい落とし穴

「コンパイルが通れば動く」という誤解

シンタックスエラーがなく、型検査も通過したとしても、論理バグ・無限ループ・計算ミスは残る。「コンパイルが通る ≠ 正しく動く」。セマンティクスの正確さはテストや検証で担保する必要がある。

回避策：単体テスト・コードレビュー・静的解析ツール（型検査、データフロー解析）の活用

型エラーはシンタックスエラー？という混乱

型エラー（TypeError: cannot add int and str）はシンタックスは正しく通過する。型チェックは「静的意味（Static Semantics）」フェーズの産物。「文法は正しいが、意味的に型規則に違反している」という位置づけ。

整理：シンタックスエラー ＝ パーサが拒否 / 型エラー ＝ 意味解析器が拒否

「セマンティクスエラーは実行時のみ」という誤解

静的型付き言語（Java・TypeScript・Rust）では、型エラー・未定義変数・スコープ違反はコンパイル前に検出できる。「セマンティクスエラー ＝ 実行時バグ」ではない。「実行後に顕在化しやすいセマンティクスエラーが存在する」という理解が正確。

整理：静的セマンティクス（コンパイル時）＋ 動的セマンティクス（実行時）の2層構造

TypeScriptの型注釈はシンタックス？セマンティクス？

const x: number = "hello" の : number は、TypeScript が JS の構文に追加したシンタックス上の拡張。しかし「string を number 型変数に代入する」のは意味解析での型エラー。両方が絡む例。実行時には型情報は消去される（型消去：Type Erasure）。

次に学ぶと良いもの

コンパイラ・インタプリタ設計

字句解析・構文解析・意味解析・コード生成の全フェーズを実装することで、シンタックス/セマンティクスの区別が実装レベルで腑に落ちる。Dragon Book（Aho ら著）が定番教科書。

型理論（Type Theory）

「型エラーは静的セマンティクス」の延長線。型システムを数学的に定式化すると、Rust の借用チェッカーや Haskell の型推論が論理的に見えてくる。Curry–Howard 対応（型＝命題・プログラム＝証明）へ発展。

形式意味論（Formal Semantics）

「セマンティクス ＝ プログラムの振る舞い」を数学的に定義する体系。操作的意味論（抽象機械の状態遷移）・指示的意味論（数学関数への写像）・公理的意味論（Hoare 論理：事前・事後条件）の3流派がある。

静的解析ツール・リンター

ESLint・Pylint・Clippy（Rust）は「シンタックスチェック」を超え、未使用変数・型不整合・セキュリティパターンなど意味レベルの問題を指摘する。シンタックス/セマンティクスの区別を理解すると、なぜリンターが「文法は通るのに警告を出す」のかが明快になる。

プラグマティクス（語用論）

自然言語学のシンタックス・セマンティクスに続く第3の柱。文脈・話者意図・暗黙の前提を扱う。プログラムでは命名規則・コメント・API 設計の「文化的慣習」に近い概念で、「意味は正しいが慣習に反する」コードへの批判に相当。

BNF / EBNF 記法

言語仕様書で構文を正確に記述するための記法（BNF：Backus-Naur Form / EBNF：Extended Backus-Naur Form）。RFC・ISO 標準・言語仕様書を読む際に必須。「シンタックスとは何か」を形式的に書いたものがBNF/EBNF。
